## P8.4 — the ledger column, the merge, the fold (scrutiny item b)

- **Migration safe for an existing DB:** `performance_ledger`'s CREATE TABLE (job_store_base.py:833) has no query column — every DB, new or existing, gets `gsc_top_queries TEXT` via the store's established `_migrate()` additive loop (sqlite_store.py:196-213): `executescript(SCHEMA)` then `ALTER TABLE … ADD COLUMN` per column inside `try/except aiosqlite.OperationalError` (idempotent, "column already exists"). SQLite ADD COLUMN is metadata-only (no table rewrite); existing rows read back NULL → the reader maps to `None` (`json.loads(row[16]) if row[16] else None`). Same pattern as the issues/images/crawl_jobs columns that predate it. Verified on the code path `init()` → `_migrate()` (sqlite_store.py:74-84).
- **ON CONFLICT cannot erase stored queries:** the upsert's new clause is `gsc_top_queries = COALESCE(excluded.gsc_top_queries, gsc_top_queries)` — a later bundle carrying no queries binds NULL (`json.dumps(...) if r.gsc_top_queries else None`), and COALESCE keeps the stored value. The fold emits `or None` for an empty merge; the router emits `None` when the bundle page has no `top_queries`. There is no write path that produces an empty-but-not-NULL list, so "later bundle must not erase" holds structurally, and the two legacy writers of the same shared INSERT (gsc.py:364, crawl.py:777) pass `None` and therefore also cannot erase. Read-side column list is one shared constant used by all three SELECTs.
- **Fold arithmetic matches P6.3:** the P8.4 merge lives INSIDE the P6.3 `fold_performance_rows` (perf_join.py:122-136), and applies P6.3's own convention — two URL variants of one page are two slices of its traffic, counts add. Per-query impressions are summed across folded records and the list re-sorted `(-imps, name)`; the single-record path keeps the router's impressions-desc order. Test 3.4 reuses P6.3's exact fixture shape (`http://www.e.com/about` + `https://e.com/about/` — the same URL pair test_performance_fold.py uses for the 100+50 clicks fold) and picks inputs where summing vs taking-one-slice changes the ORDER, not just the number, so the assertion cannot pass on a wrong implementation. Test 4.9b in the P6.3 file (`_sum` keeps all-None as None) still passes — the new code only touches records that have queries.
- **Precedence & fallback:** striking distance reads ledger queries first, falls back to the scan-time seed (striking_distance.py:76-80). 3.5 (seed supplies queries when ledger empty — the regression the obvious implementation causes) and 3.6 (ledger wins over a stale seed) both pass. `deferred` no longer names `top_queries` (performance.py:284-291); the site-level query report stays deferred and is asserted deferred in the renamed in-place test.

2. **P8.1 residual — the `regenerate` route still writes a whole snapshot.** `POST /fix-focus/regenerate` (crawl.py:2588) reads the snapshot at request start (`get_job`), rebuilds from current issues, merges checked state from that read, and persists via `_load_or_build_fix_focus`'s whole-snapshot `update_job` (crawl.py:2563) — outside `mutate_fix_focus`. 3. **`issue_checker.py:240` binds an import-time copy of the same constant** (`page_size_limit_kb: int = _DEFAULT_PAGE_SIZE_LIMIT_KB`) — the exact "copy, not reference" pattern P8.3's test 3.3 exists to reject, one level down. Cosmetic; the spec only demands impressions-descending. The fold path's name tiebreak is the deterministic one — if the router's sort ever matters for ties it could use the same key.
