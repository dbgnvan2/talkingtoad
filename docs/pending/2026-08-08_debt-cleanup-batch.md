## CLN1 — Drop the dead `duplicate` category + forbid future dead categories

**Problem (P2/P10).** `"duplicate"` appears in `Results.jsx` CATEGORIES,
`SummaryPanel.jsx` CATEGORIES, and `report_generator.py` `cat_list`, but **no
`_CATALOGUE` `_IssueSpec` emits `category="duplicate"`** (verified 2026-08-08:
`grep 'category="duplicate"'` on `registry.py` returns nothing; near-duplicate
detection lives under other categories). So the "Duplicates" tile/row is
permanently `0` — a misleading dead surface. The new parity test only checks for
*missing* categories, so it does not catch this *extra* key.

**Fix.**
1. Confirm (grep) that no `_IssueSpec` uses `category="duplicate"`. If any
   duplicate-detection code *should* be its own category, the alternative is to
   wire it — but current evidence says **drop**.
2. Remove the `duplicate` entry from all three lists.
3. Tighten `test_category_display_lists_cover_every_backend_category` to also
   assert **no extra keys** — i.e. each display list's key set equals the backend
   category set exactly (`keys ^ backend == ∅`), not just `backend ⊆ keys`. This
   makes a dead category impossible to (re-)add.

**Acceptance → test.**
| ID | Criterion | Test |
|---|---|---|
| CLN1.1 | No `_IssueSpec` emits `category="duplicate"` (guards the premise). | `tests/test_frontend_backend_code_parity.py::test_cln1_1_no_dead_duplicate_category` |
| CLN1.2 | Each of the 3 display lists' key set **equals** the backend category set (no missing, no extra). | extend `test_category_display_lists_cover_every_backend_category` (bidirectional) |

**Priority: MEDIUM-LOW** (quick, removes a misleading UI/PDF surface).

## CLN2 — Single source of truth for the category list

**Problem.** The category set is hand-mirrored in 4 places (registry + 2 frontend
arrays + PDF `cat_list`). The parity test (CLN1) *binds* them so drift fails CI,
but the durable fix is to stop mirroring.

**Fix.** Extend the `docs/issue-codes.md` generator to also emit a generated
`frontend/src/data/categories.generated.json` (`[{key, label}]`, ordered) derived
from the registry. `Results.jsx`, `SummaryPanel.jsx`, and the PDF `cat_list` read
from that single generated source (the PDF via a small Python loader of the same
JSON, or directly from the registry). Labels live in the generator so they stay
editorial-content-out-of-logic.

**Acceptance → test.**
| ID | Criterion | Test |
|---|---|---|
| CLN2.1 | `categories.generated.json` matches the registry category set + is regenerated by the generator (drift fails, like `issue-codes.md`). | generator-sync test alongside the existing `issue-codes.md` sync test |
| CLN2.2 | Both frontend arrays and the PDF list are sourced from the generated file (no hand-maintained category literals remain). | grep-based architecture test: no literal `CATEGORIES = [` object list in the two JSX files once migrated |

**Priority: LOW** (the CLN1 parity test already prevents the failure mode; this is
the durable-but-optional refactor). **Effort: MEDIUM.** May warrant its own focused
spec at implementation time. Depends on CLN1 (drop the dead key first).

## CLN3 — Complete `_ANALYSIS_CATEGORY_MAP` (defensive; not currently reachable)

**Finding (P3, latent).** In `api/crawler/engine.py`, `_ANALYSIS_CATEGORY_MAP`
covers 9 of 13 categories; `security`, `image`, `rendering`, `semantic_html`
belong to **no** toggle group. Under a *partial* `enabled_analyses`,
`_enabled_categories` would silently exclude those four with no toggle to enable
them.

**Current reachability: NOT user-facing** (verified 2026-08-08: the frontend sends
no partial `enabled_analyses` for crawls — every crawl runs with
`enabled_analyses=None` ⇒ all categories). So this is a **latent risk /
defensive guard**, not a live bug. It becomes live the moment a partial-analysis
UI is added.

**Fix.**
1. Map the four orphan categories to groups (extend existing groups, e.g. add
   `security` under a new/existing "technical" group and `image` under an "images"
   group; `rendering` + `semantic_html` under `ai_readiness` or a new
   "agent_readiness" group), **or** add an explicit always-run set the resolver
   unions in regardless of selection.
2. Add a completeness guard test.

**Acceptance → test.**
| ID | Criterion | Test |
|---|---|---|
| CLN3.1 | The union of `_ANALYSIS_CATEGORY_MAP` values **equals** the backend category set (minus `duplicate` after CLN1) — no category is unreachable via toggles. | `tests/test_engine_analysis_map.py::test_cln3_1_map_covers_every_category` |
| CLN3.2 | `_enabled_categories(None)` returns `None` (all-on) — regression guard for the default full crawl. | same file |

**Priority: LOW** (defensive, cheap). Do it before any partial-analysis-toggle UI.

## CLN4 — Unify the GSC ledger join key (sweep finding F4)

**Problem (P3/P6).** Legacy `/api/gsc/ingest` (`api/routers/gsc.py:283`) writes
ledger rows keyed on the **raw GSC URL** and leaves `source_generated_at=None`,
whereas the bundle ingest + the page-priority consumer (`crawl.py:1335`) key on
the **crawled-page URL**. When the GSC URL form differs (trailing slash / `www` /
scheme), the GSC row lands under a key nothing reads — the data is stored but
never surfaces. (GA4 is COALESCE-preserved, so no data is lost, but GSC rows can
be orphaned.)

**Fix.** Factor `_match_key` out of `api/routers/performance.py` into a shared
module (e.g. `api/services/perf_join.py`); route both `gsc.py` and
`performance.py` through it so GSC rows are stored under the crawled-page key.
Stamp `source_generated_at` on GSC ingest (the ingest timestamp, passed in — not
`Date.now()` in a workflow-unsafe spot). Match bundle-ingest semantics: unmatched
GSC URLs are reported/held-out, not orphaned.

**Acceptance → test.**
| ID | Criterion | Test |
|---|---|---|
| CLN4.1 | A GSC URL differing from the crawled page by trailing-slash / `www` / scheme is stored under the **crawled-page** key and is read back by the page-priority consumer. | `tests/test_gsc_integration.py::test_cln4_1_gsc_ingest_joins_on_crawled_key` |
| CLN4.2 | GSC-ingested rows carry a non-null `source_generated_at`. | same file |
| CLN4.3 | `_match_key` has one definition, imported by both routers (no duplication). | architecture/grep test |

**Priority: MEDIUM** (correctness — GSC data may silently not surface for
URL-form-mismatched sites, which is common with `sc-domain` properties).

## CLN7 — `/pages` scoped issue query (sweep finding P9)

**Problem.** `get_pages` (`crawl.py:784`) calls `store.get_all_issues(job_id)` and
reconstructs every `Issue` on **every** paginated request, just to grade the ≤50
URLs shown. On a large crawl (~10k rows at the 500-page default) each page-flip
re-materialises all rows.

**Fix.** Scope the issue load to the page's URLs (`WHERE page_url IN (<the 50>)`),
or push the `ai_readiness` impact rollup into the same SQL aggregate that already
computes `issue_counts`. Store-level change across **both** SQLite and Redis.

**Acceptance → test (real-scale, P9).**
| ID | Criterion | Test |
|---|---|---|
| CLN7.1 | `/pages?limit=50` on a job with many issues loads issues for only the returned URLs (assert via a query/row-count probe or a spy on `get_all_issues`), not the full set. | `tests/test_api.py::test_cln7_1_pages_scopes_issue_load` |

**Priority: LOW** for the nonprofit target (≤500 pages), but a real amplification.
**Effort: MEDIUM** (store change, both backends). May warrant its own focused spec.
